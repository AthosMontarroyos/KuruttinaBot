# Website

A implementação atual usa React, TypeScript, Tailwind, Vite e servidor Node em `apps/site/server`. A direção aprovada é React sem Next.js, construindo uma base/framework próprio com liberdade de organização. Estrutura de pastas e roteamento são decisões do projeto, não convenções impostas por um framework. Veja a [decisão](../../../docs/decisions/react-base.md). Autenticação (OAuth Discord) e painel já existem; o login é exclusivamente Discord, conforme a [decisão de autenticação](../../../docs/decisions/discord-only-authentication.md).

Rotas ficam em pastas sob `src/app/`, uma pasta por segmento de URL, com `page.tsx` como arquivo da rota (`app/login/page.tsx` → `/login`); segmento dinâmico usa colchetes (`app/dashboard/[serverId]/page.tsx` → `/dashboard/:serverId`). Uma aba ou seção sem URL própria — por exemplo visão geral, Mensagens e módulos dentro do painel de um servidor — **é visualização, não rota**: o `page.tsx` da rota guarda o estado de qual visualização mostrar, e cada visualização tem sua própria pasta dentro da pasta da rota, com o arquivo principal chamado `view.tsx` (nunca `page.tsx`, para não ser confundida com rota) — ex.: `dashboard/[serverId]/overview/view.tsx`, `.../messages/view.tsx`. Código que só essa visualização usa (dados, subcomponentes) fica dentro da pasta dela, como `.../messages/templates-api.ts`. Só promova uma visualização a rota (com `page.tsx` próprio) quando precisar de URL própria, recarregável e compartilhável. Código usado por mais de uma rota ou visualização vai para `src/components/` ou `src/lib/`.

   **Dados do bot na tela (MUST).** A página `/comandos` (`src/app/comandos/`, `src/components/commands/`) lê `COMMAND_CATALOG` de `@kuruttina/command-catalog/catalog`, um arquivo gerado a partir dos módulos de `apps/bot/src/commands/` por `scripts/commands-catalog.mjs`, que `npm run site build` e `npm run typecheck` executam sozinhos. Nunca edite `packages/command-catalog/catalog.js` nem escreva a lista de commands na página; o site não importa nada de `apps/bot`. Command novo, editado ou removido aparece depois do próximo build, sem outra edição.

Links internos da Home são `<a href>` normais. `src/lib/navigation.ts` (`usePathname`, usado no layout) intercepta o clique simples e troca a tela com `history.pushState`, sem recarregar a página. Não reimplemente o roteador: um `<a href="/caminho">` já entra nesse fluxo. Clique com modificador, outro destino, download, outra origem, âncora na mesma página e rotas do servidor (`/auth/*`, `/api/*`, como o `/auth/discord` do login) continuam no navegador: o servidor responde com redirecionamento, que uma troca de tela não faria. `location.replace` fica só para redirecionar sessão (login e painel).

**Editor de mensagens (reutilizável).** Qualquer módulo que deixe o administrador escrever uma mensagem do bot (modelos, chegada, saída...) usa `src/components/message-editor/MessageEditor.tsx` (`MessageEditor` para editar, `MessagePreview` para só mostrar), sem recriar campos de embed nem prévia. Ele recebe e devolve o JSON do modelo (`initialJson`/`onChange`, com `label` e `allowJson` opcionais) e lê o valor só ao montar: troque a `key` para carregar outra mensagem. A formatação estilo Discord (negrito, listas, código...) fica em `markdown-format.ts`, lógica pura com testes em `tests/markdown-format.test.ts`. Erro de formato do modelo é explicado por `describeTemplateIssue` em `format-issue.ts` (testes em `tests/format-issue.test.ts`): a frase aponta o campo e o que falta, em vez de repetir a mensagem crua da validação. Mudou um campo do embed? Atualize o modelo em `packages/message-templates` (validação, `render.js`) e a conversão do bot (`toCommandReply.ts`) junto.

Entrada e saída de membros usa o editor com `allowComponents={false}` (sem Action Rows). Abas do editor: Visual, JSON, Variáveis e Enviar (esta só com a prop `sendPanel`). A lista de variáveis é a do pacote (`ACTION_VARIABLES`, importada de `@kuruttina/message-templates/variables`); nunca copie a lista no site. O preview troca variáveis por valores de exemplo em `preview-values.tsx` (bot no papel do usuário, servidor aberto no painel) e campo de imagem com `{variável de imagem}` mostra a imagem. Ao mexer em variável, preview ou lista de modelos, leia [editor de mensagens](../../../docs/project/message-editor.md). Botão de apagar usa a lixeira com hover vermelho, não texto.

**Seletores (reutilizáveis).** Qualquer módulo que precise de um canal, cargo ou categoria do servidor (enviar mensagem, chegada, saída, grupos de cargo...) usa `ChannelSelect`, `RoleSelect` ou `CategorySelect` de `src/components/selectors/` (`guildId`, `value`, `onChange`, `label` opcional), nunca um campo de ID solto. Um seletor novo (membros, emojis...) é um arquivo fino nessa pasta sobre `ResourceSelect.tsx`, que cuida de carregar, falhar, tentar de novo e aceitar o ID digitado. As listas vêm de `GET /api/guilds/:guildId/channels|categories|roles` (`server/guild.ts`), que o servidor do site responde consultando o Discord com o token do bot em `server/discord.ts`. Para vários cargos use `RoleMultiPicker` (`selectors/RoleMultiPicker.tsx`): painel flutuante sobre o elemento `anchor` (a engrenagem da função abre o dele sobre o chip), com chips de cor, + e busca; não ocupa espaço no formulário nem vira campo fixo. Leituras novas do Discord entram em `server/discord.ts`, nunca no `src/`, e seguem os controles da [decisão do token do bot](../../../docs/decisions/site-holds-bot-token.md): o token não pode ir ao bundle, a respostas, a logs nem à configuração serializável.

**Controles de formulário (reutilizáveis).** Opção de ligar ou desligar usa `SwitchField` (`src/components/Switch.tsx`: `label`, `description`, `checked`, `onChange`, `boxed`), nunca um `<input type="checkbox">` solto; quando o rótulo tem layout próprio, use `Switch` com `labelledBy`. Escolha entre poucas opções de um mesmo formulário (Entrada/Saída) usa `SegmentedControl` (`src/components/SegmentedControl.tsx`). Não copie o visual desses controles.

**Autocompletar do editor.** Nos campos de texto do `MessageEditor`, `:` abre os emojis do servidor, `#` os canais (texto e voz) e `@` os cargos; escolher grava `<:nome:id>`, `<#id>` ou `<@&id>`. A lógica pura está em `message-editor/autocomplete.ts` (testes em `tests/message-autocomplete.test.ts`), o painel em `SuggestionPanel.tsx`, as listas em `guild-resources.tsx` (carregadas só quando precisam, uma vez por servidor) e a prévia desses formatos em `markdown-format.ts` (`parseInline`). Campo novo de texto do editor usa `InlineText` (já traz o autocompletar; `suggest={false}` onde o Discord não renderiza emoji nem menção, como autor e rodapé). Detalhes em [editor de mensagens](../../../docs/project/message-editor.md).

## Procedimento

1. Localize o componente ou boundary HTTP afetado. Leia [Home local](../../../docs/project/site.md) para execução/configuração; consulte [referência visual da Home](references/home.md) somente para layout e proveniência visual. Ao desenhar ou rever outra página pública, leia [capa da Home](references/cover-design.md): é a linguagem visual aprovada (ilustração como protagonista, palco claro, título em serifa) a ser estendida.
2. Todo botão que salva, cria ou envia no painel usa `SaveButton` (`app/dashboard/ui.tsx`: `saving`, `savingLabel`, `size`, `attention`, `variant` `solid` ou `outline` para ações secundárias como "Testar"), nunca um `primaryButton` com texto trocado à mão: o visual e o spinner de "Salvando…" são sempre os mesmos e só o texto, o tamanho e o que ele grava mudam.
3. Em UI, mantenha componentes em `src/`, estados de indisponibilidade honestos, teclado/foco e variantes desktop/celular. Confira os estados e larguras afetados no browser quando possível; registre se essa validação não foi executada.
   **Sem observações de desenvolvimento no design (MUST).** Todo texto visível ou lido por tecnologia assistiva (UI, avisos, placeholders, `title`, `aria-label`, mensagens de erro) é texto de produto. Não mencione protótipo, mock, exemplo, ambiente, variável, ID, token, "ainda não configurado", "em desenvolvimento" nem status de implementação. Indisponibilidade usa texto neutro de produto ("estará disponível em breve"); páginas pedidas como "em construção" dizem só isso. Ferramenta de desenvolvimento (login mock) aparece só quando o servidor a habilita em development e sem legenda explicativa. Observações para quem desenvolve ficam em comentários de código ou em `docs/`. Antes de concluir uma tarefa de UI, procure esses termos nos textos alterados.
4. Em SVG ou mídia, leia as seções correspondentes de [assets](../project-operations/references/assets.md). Ícones locais ficam por função em `public/icons/`; caminho público e allowlist mudam juntos. Mídia R2 permanece remota. Ícone do app (TopBar) e foto do bot (Home) vêm do Discord pelo servidor, nunca de arquivo no repositório. Cores do site são sempre tokens de `globals.css` (paleta rosa), nunca hex solto.
5. Em HTTP, CSP, arquivos públicos ou configuração, leia entrada, XSS, secrets e erros em [segurança](../project-maintenance/references/security.md). Antes de diagnosticar host, porta ou URL, identifique o modo em [desenvolvimento](../../../docs/project/development.md) e o comportamento em [Home local](../../../docs/project/site.md). A publicação fica na [referência de deployment](../project-operations/references/deployment.md). Preserve a configuração automática: `npm run site dev` seleciona development pelo preload `@kuruttina/config/site-development`; sem `SITE_URL`, development deriva a URL de `PORT`; produção recebe a origem explícita pelo Compose. Não derive origem pública de headers ou de `HOST`. Mantenha publicação allowlisted, GET/HEAD, limites, shutdown e o `/healthz` existente. Nunca envie secrets ao bundle.
6. Para conferir UI no Docker de desenvolvimento, reconstrua com o comando de [deployment](../project-operations/references/deployment.md) e entre de novo pelo "Entrar como dev": a recriação dos contêineres derruba a sessão. Execute `npm run typecheck`, `npx vitest run tests/site.test.ts` e `npm run site build`. Build limpa somente o destino do site. O servidor nativo (`npm run site dev`, ou o preview do app) guarda o pacote em memória: depois de `npm run site build`, reinicie-o para ver a mudança. Mudança no código do bot pede reconstruir só o contêiner dele, `doppler run -- docker compose -f compose.dev.yaml up --build -d bot`, sem derrubar as sessões do site. Migration nova só é aplicada no banco de desenvolvimento com autorização do responsável. Para novos fluxos críticos, selecione os testes adicionais em [validação](../project-maintenance/references/validation.md).

## Login e administração, somente quando pedidos

A [decisão de login exclusivo via Discord](../../../docs/decisions/discord-only-authentication.md) é requisito obrigatório de qualquer trabalho de autenticação ou painel.

Leia [autenticação e administração](references/authentication-and-admin.md): mutations, identidade Discord, autorização pela equipe, sessões, CSRF, erros e administração aplicam-se ao fluxo correspondente. O DevMock só existe com `APP_ENV=development` e lê o dev ativo por `getActiveDevUserId()` em `@kuruttina/database`, nunca por `OWNER_ID`. Persistência aciona `database-developer`; publicação e hospedagem acionam `project-operations`. Não crie contas, usuários de teste ou registros privilegiados sem autorização explícita do responsável.

Atualize esta skill quando mudar o procedimento de trabalho e `docs/project/site.md` quando mudar o comportamento implementado, sem duplicar os dois.
