# Home local

A primeira Home foi adaptada dos frames desktop e celular do [Figma](https://www.figma.com/design/GQNMJgri0cuH6IuiFSJ6Qx/Kuruttina-Home?node-id=0-1). O código está em `apps/site`. Layout, proveniência dos ícones e imagem provisória estão em [referência visual](../../.claude/skills/website-developer/references/home-figma.md).

Com as dependências instaladas pelo lockfile (`npm ci`), o modo nativo recebe do Doppler `ASSETS_BASE_URL` (origem HTTPS pública do bucket), `DATABASE_CA` e `SITE_DATABASE_URL` (role `kuruttina_site`, lida pelo processo como `DATABASE_URL`). Os configs `dev` e `prd` precisam de `SITE_DATABASE_URL`. `PORT` continua opcional no processo (padrão `3666`). O comando `npm run site dev` define `APP_ENV=development`; a URL pública local é calculada pela porta quando `SITE_URL` está ausente. `npm run site dev` não chama o Doppler. O preload `@kuruttina/config/site-development` copia `SITE_DATABASE_URL` para `DATABASE_URL` quando esse valor está presente. Execute `doppler run --only-secrets ASSETS_BASE_URL,SITE_DATABASE_URL,DATABASE_CA,DISCORD_BOT_TOKEN -- npm run site dev` e abra `http://127.0.0.1:3666`. O DevMock usa o dev ativo do banco; `DISCORD_BOT_TOKEN` lista os servidores. `OWNER_ID` não entra nesse comando. Sem `HOST`, ou com `HOST` em branco, o processo escuta `127.0.0.1`. Um `HOST` informado precisa ser um endereço IP.

Nos contêineres o serviço do site fixa `HOST=0.0.0.0`: o processo escuta em todas as interfaces dentro do contêiner, e o Compose publica somente o loopback do host. Produção fica em `127.0.0.1:3666`; o Compose de desenvolvimento fica em `127.0.0.1:3667`. O log `Home local:` mostra o endereço de escuta do processo, que dentro do contêiner é `0.0.0.0`. `APP_ENV`, `HOST`, `PORT` e `SITE_URL` são fixos no Compose e não vêm do Doppler. Development usa `http://localhost:3667`; production usa `https://kuruttina.athosmontarroyos.com`. Os três modos estão em [desenvolvimento](development.md).

O processo é separado do bot e usa a conexão da role `kuruttina_site`. `SITE_URL` é a origem pública da Home, distinta do endereço de escuta e da porta publicada. Em desenvolvimento nativo ela é `http://localhost:3666`; no Compose de desenvolvimento, `http://localhost:3667`; em produção, `https://kuruttina.athosmontarroyos.com`. A porta e o endereço de escuta não derivam dessa URL.

A interface está em React, TypeScript e Tailwind, organizada como `src/app` e `src/components`. Os SVGs de interface ficam em `public/icons/`, um diretório por função (`theme`, `account`, `language`, `community`, `social`). O processo HTTP fica em `server/`. `npm run site build` limpa somente `dist/apps/site`, gera o bundle com Vite e compila o servidor Node. `npm run site start` executa esse build com ambiente explícito no processo; em production, exige também `SITE_URL`. Use `npm run site dev` para selecionar development automaticamente. Reinicie após alterações. `npm run typecheck` verifica o servidor e os componentes, e `npm test` inclui os testes HTTP/configuração, sem ler `.env` operacional.

A composição valida ambiente, porta e URL de assets no startup. A página carrega `icons/Icons/1.jpg` diretamente do R2, tanto no avatar quanto no retrato. Para trocar a imagem, altere a chave relativa em `apps/site/server/config.ts`. Nenhuma credencial Cloudflare entra no processo ou no browser. A fonte Outfit é carregada pelo Google Fonts; se indisponível, há fallback sans-serif. Falha de mídia mostra alternativa textual no retrato.

A troca de tema funciona com armazenamento local opcional. `/login` é a página de entrada; o ícone da conta no topo leva a ela e, logado, vira a foto do Discord com menu (Painel de controle, Sair). `/dashboard` lista os servidores que o usuário administra; escolher um navega para `/dashboard/<id do servidor>`, o painel desse servidor, com visão geral (membros e ID), **Mensagens** (templates do servidor; salvar a edição permanece na mesma tela e, enquanto houver alteração, um aviso no topo informa que ainda não foi salvo, o aviso de salvo some sozinho, e um formato incompleto aponta o campo e o que falta) e módulos (em construção) como visualizações internas, sem URL própria. Sem sessão, as duas rotas redirecionam para `/login`; um ID de servidor inexistente ou fora da lista do usuário mostra aviso com link de volta a `/dashboard`. O login real é OAuth do Discord (`/auth/discord` → `/auth/callback`, scopes `identify guilds`, `state` ligado a cookie e PKCE S256), com o client id do bot (`DISCORD_BOT_ID`) e `DISCORD_CLIENT_SECRET`; a redirect URI `SITE_URL/auth/callback` precisa estar cadastrada no Developer Portal. O servidor troca o código, lê a identidade e os servidores em que o usuário gerencia (dono, Administrador ou Gerenciar servidor), descarta o access token e guarda a lista e o Discord ID na sessão — o ID nunca é devolvido ao navegador, só serve para auditoria no servidor (quem criou/editou um template). Sessão em memória: cookie `HttpOnly`, `SameSite=Strict`, 7 dias sem uso (cada acesso renova) e no máximo 14 dias desde o login, só o hash do token no servidor, gravada em `.sessions/` em development para sobreviver a reinícios (`SESSION_FILE` muda ou desliga o caminho; em production só persiste se informado); `GET /api/session` informa o estado; `POST /api/logout` exige `Origin` igual a `SITE_URL`. `GET /api/guilds/<id>/channels`, `/categories` e `/roles` listam, para quem administra o servidor (sessão e permissão checadas antes), os canais de texto e de anúncio, as categorias e os cargos (sem `@everyone`), lidos no Discord com o token do bot e guardados 30 segundos em memória; o painel os usa nos seletores `ChannelSelect`, `CategorySelect` e `RoleSelect` (`src/components/selectors/`), por exemplo ao enviar uma mensagem a um canal. Em development (`APP_ENV=development`) há também o DevMock (`POST /api/mock-login`, mesma checagem de `Origin`). A identidade é o registro ativo de papel `dev` em `bot_private.bot_staff`, lido pela função `active_dev_user_id()`. Sem esse registro, o login mock responde `dev_ausente` e não abre sessão. Como não há token do usuário, o DevMock lista os servidores do bot onde esse usuário é membro, usando `DISCORD_BOT_TOKEN`. Sem o token, a sessão abre sem servidores e com o rótulo Dev. `DISCORD_BOT_ID` não entra no DevMock: continua sendo o client id do OAuth, junto com `DISCORD_CLIENT_SECRET`. O Compose de desenvolvimento entrega `DISCORD_BOT_TOKEN` ao site e não entrega `OWNER_ID` nem `DISCORD_BOT_ID`. O Compose de produção também entrega `DISCORD_BOT_TOKEN` ao site, para a lista de canais ([decisão](../decisions/site-holds-bot-token.md)), e não habilita o DevMock. `OWNER_ID` não é lido e pode ser apagado do config Doppler `dev`. Segredos vêm do Doppler. A credencial do site é `SITE_DATABASE_URL` (role `kuruttina_site`). `npm run site dev` não chama o Doppler; o preload copia esse valor para `DATABASE_URL`, com `DATABASE_CA`. O bot não recebe `SITE_DATABASE_URL`. Exemplo: `--only-secrets ASSETS_BASE_URL,SITE_DATABASE_URL,DATABASE_CA,DISCORD_BOT_ID,DISCORD_CLIENT_SECRET,DISCORD_BOT_TOKEN -- npm run site dev`. Abaixo de 701 px o cabeçalho vira barra compacta com menu e tema. `/comandos` e `/modulos` são páginas "em construção" (o servidor entrega o mesmo HTML e o cliente escolhe a página pelo caminho). Um clique simples em link interno troca a tela sem recarregar e o histórico do navegador continua valendo; clique com modificador, outro destino, download, outra origem ou âncora na mesma página segue o navegador. O servidor reconhece `/dashboard/<id>` pelo formato de snowflake do Discord e entrega a mesma casca. O ícone do Discord na Home é o servidor de suporte. Termos, convite, conta, servidor de suporte e redes sociais ainda precisam de conteúdo/integração; seus controles informam essa indisponibilidade. A direção aprovada em 15 de outubro de 2026 é [login exclusivo via Discord](../decisions/discord-only-authentication.md).

A administração de templates de mensagem (`/api/guilds/:guildId/templates`, método GET/POST/PUT/DELETE conforme a ação) exige sessão autenticada e que o servidor esteja entre os que o usuário administra (mesma lista da sessão); mutations exigem `Origin` igual a `SITE_URL`, como `/api/logout`. O site acessa `bot_private.message_templates` com uma role de runtime própria, `kuruttina_site` (distinta de `kuruttina_bot`, [decisão](../decisions/site-owns-template-config.md)), sem `SELECT` em `bot_settings`/`bot_staff`. A única leitura de equipe é `bot_private.active_dev_user_id()`, que devolve só o `user_id` do registro ativo com papel `dev`, para o DevMock. A validação de regra de negócio (nome, tamanho do JSON, limites do Discord, cota por servidor) vem do pacote compartilhado `packages/message-templates`, o mesmo que o bot usa; o site não importa nada de dentro de `apps/bot`.

Publicação na VPS não confirmada. A decisão vigente coloca esta Home em contêiner na VPS, com o `cloudflared` do host apontando para `http://127.0.0.1:3666`. A unidade `kuruttina-site` é o runtime anterior. O servidor continua expondo somente arquivos públicos allowlisted e `/healthz`, com GET/HEAD, CSP, timeout HTTP e encerramento limitado após sinais. Nenhuma configuração de produção foi aplicada fora do repositório.
